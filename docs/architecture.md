# Architecture

## Local scan jobs

Live local mode exposes `POST /api/v1/scan-jobs` with `{ "wallet": "0x…" | "name.eth" }`, `GET /api/v1/scan-jobs/active`, `GET /api/v1/scan-jobs/{job_id}`, and `GET /api/v1/wallets`. Active discovery reports the one queued or running process-local job, or `null`; it is an API capability for local clients, not durable job history. The job manager uses the typed server-side ENS resolver at one finalized observation block and serializes work through one local worker. A scan target is the wallet's missing range through that finalized head; the response records bounds, progress, and resolver observation provenance. The bundled subprocess indexes that bounded range in an isolated Envio schema, polls persisted progress until the exact end is ready, terminates/reaps the long-lived Envio process, validates finalized evidence, merges shared raw rows/checkpoints, runs dbt against the staged complete artifact, and removes its temporary schema. Early exit and bounded timeout are failures. `WALLET_SCAN_COMMAND` remains an optional adapter override. The manager independently validates finalized provenance plus preservation of canonical event identities, immutable event facts, shared RPC observations, run history, and application-owned state before atomic publication. Recomputed dbt summaries are validated by dbt and may replace prior aggregate rows when new events change their counts.

Workers update a temporary sibling copy of the complete artifact. The manager calls `os.replace` only after the worker exits successfully, the artifact exists, the selected wallet has matching finalized provenance, and no existing wallet was dropped; failed jobs therefore leave the previously served `live.duckdb` untouched. All completed wallet identities remain in the wallet list, while a completed job causes the dashboard to reload and automatically use the newly selected wallet. Fixture/static mode does not call these routes and disables scan controls.

The primary product is a locally run, database-backed wallet analytics application. HyperIndex captures a narrow event set, dbt turns those events into DuckDB marts, a local API queries those marts on demand, and React renders the API responses. Static JSON is a separate fixture-only portfolio demo for GitHub Pages.

## Flow

1. `indexer/` runs Envio HyperIndex on Ethereum mainnet.
2. Before a live scan run is created, the server-side scan-input boundary accepts a normalized address or conservative ASCII ENS name. ENS input uses the pinned mainnet ENS registry and returned resolver at one Ethereum `finalized` block; unresolved or unsupported names raise `ENSNotRecognizedError` and never become an index target. The original input, normalized name, resolved address, resolver source, observation block number/hash, and block timestamp are carried into the selected wallet's existing `ops.pipeline_runs` row.
3. The HyperIndex handler stores one `Erc20Transfer` entity per wallet-relevant `Transfer(address,address,uint256)` log. This is intended for ERC-20 analytics, but ERC-721 uses the identical signature and the wildcard source currently has no standards-disambiguation step. It persists the canonical block hash provided with each event and selects the top-level transaction `from` and `to` fields, then stores them alongside the emitted Transfer `from`, `to`, and raw third value. Transaction-envelope evidence remains nullable during the historical migration. HyperIndex raw-event storage is disabled because the normalized entity is the pipeline input and duplicate raw storage adds overhead.
4. In local-product mode, each run selects one wallet interval, pins a finalized end hash, records wallet-scoped provenance, and lets dbt-duckdb attach HyperIndex Postgres read-only. Live staging reads each available durable raw relation: Envio's normal `public."Erc20Transfer"`, shared `wallet_scan.transfer_events`, or both; a build with neither fails explicitly. When both exist, they are deduplicated by `(chain_id, transaction_hash, log_index)` and the build fails if duplicate identities disagree on immutable evidence. Dashboard jobs populate the shared source through a temporary bounded Envio schema only after its `envio_chains` checkpoint proves full-range completion and RPC confirms the finalized endpoint hash. The raw merge and `wallet_scan.ingestion_runs` checkpoint commit together, including zero-event ranges. A retry with a newer finalized endpoint reuses contiguous completed checkpoints from the still-missing start and indexes only the uncheckpointed tail. dbt then incrementally updates the selected wallet in the staged complete artifact while retaining prior wallet projections. Fixture mode remains separate and deterministic.
5. In live mode, dbt joins offline token inputs and the ignored `analytics/artifacts/account_evidence.duckdb` cache, separates metadata availability from token recognition, and materializes one complete semantic event relation inside the analytics artifact. Materialization is required because the HyperIndex and account-evidence attachments exist only during the dbt session; the standalone DuckDB must retain row-level raw evidence after they are detached. Each dashboard mart is an independent, purpose-built projection from that relation rather than a downstream copy of another serving mart. The historical fixture uses reviewed pinned account evidence; the separate synthetic test dataset supplies an empty typed relation rather than invented classifications.
6. The local FastAPI service opens `analytics/artifacts/live.duckdb` and queries complete marts for the process-level selected wallet. `EVM_WALLET_SCAN_ADDRESS` selects the wallet when set; when unset, the API derives the default only from an artifact containing exactly one metadata wallet and rejects zero or multiple wallets. It owns one isolated mutable table for manual token-recognition overrides. It binds to loopback, requires HyperIndex provenance backed by a completed finalized run, and never serves the fixture database in production mode.
7. The Vite React dashboard calls the local API. Browser code never receives a Postgres DSN, DuckDB write access, or RPC credentials.
8. Separately, `scripts/export_dashboard.py` reads only `analytics/artifacts/fixture.duckdb` and creates bounded fixture JSON under `public/data/` for the GitHub Pages demo. Vite selects the live API adapter for `dashboard:dev` and the static adapter for `dashboard:build`; the two sources are never configured together.

## Local Application Contract


The local API is the serving boundary. It accepts `recognition=all|recognized|other`, with effective recognition resolved from a manual override before the automatic registry result. Within the repeated `account` query parameter, selected values use OR semantics; omission selects every value, while the exclusive `account=none` sentinel preserves an intentionally empty UI selection. The optional literal substring query applies to dashboard-visible transaction, wallet, counterparty, token-address, token-symbol, and token-name fields. An optional UTC `start` date is inclusive and `end` date is exclusive; both are required together and compose with the other predicates using AND semantics. Summary, event, timeline, and token endpoints apply all predicates directly. The counterparty endpoint uses recognition as inclusive cohort membership: at least one selected-status event makes an address eligible, then its complete activity inside the remaining account/search/time scope is aggregated and ranked. The API computes only the selection requested by the user; it does not precompute every possible selection.

API responses identify the configured wallet and chain, pinned configured label, DuckDB transformation generation time, that wallet's cumulative finalized snapshot bounds and end-block hash, observed event block/time bounds, population-reconciled account-evidence coverage, API schema version, and `completeness_scope: finalized_block_range`. The explicit `dashboard-api-v16` metadata projection does not expose internal mart columns accidentally. Before serving live data, the API verifies contiguous completed intervals independently per wallet and reconciles each wallet's cumulative `events_found` with its snapshot transfer count. Account coverage uses every distinct nonzero, nonself event counterparty in the current snapshot as its address denominator and the corresponding captured Transfer-signature rows as its event denominator. Each denominator reconciles into classified, failed, and not-checked counts; successful-observation block/time bounds are reported separately. Cached evidence for addresses outside the current population cannot inflate coverage. The event extrema remain separate and are not used to infer continuity. Ranked responses distinguish the exact complete matching item count from the returned top-N limit and disclose `is_truncated`. Events use stable descending block/transaction/log keyset pagination, disclose the exact complete matching event count, and return an opaque next cursor. Browser responses expose only the identifiers, display metadata, classifications, and counts required by the current dashboard. Exact raw values, decimals, and detailed provenance remain in the complete DuckDB intermediate relation rather than being repeated in serving marts or payloads. Every API response sets `is_sampled: false`; bounded ranking and pagination are presentation constraints, not source sampling. The default static snapshot also carries recorded finalized coverage, while the separate synthetic test dataset keeps coverage null.

React must not connect directly to HyperIndex Postgres or DuckDB. “Database-backed” means the local server owns DuckDB connections and exposes a typed application API. HyperIndex Postgres remains ingestion persistence rather than a browser-facing query service. All analytics relations are dbt-owned; only `app.token_recognition_overrides` is application-owned mutable state.

Manual recognition overrides are one row per `(chain_id, token_address)` with status `recognized` or `other` and an update timestamp. The API validates that the address is present in the current analytics snapshot. A manual row takes precedence over automatic exact-address registry classification in every query; deleting it resets the token to automatic. The live dashboard changes this state immediately and offers one four-second Undo action that restores the exact previous override, including no row. Fixture-demo controls are read-only. Normal in-place dbt builds do not own or replace the `app` schema, so overrides persist across analytics refreshes. The scan-job manager copies this application-owned table into a successful staged artifact before replacing `live.duckdb`; explicitly deleting the artifact still deletes this local state, an accepted MVP durability limit.

## Dashboard Behavior

In live mode, React sends recognition, binary address-type, literal text-search, and selected UTC-period predicates to the API. They are applied before summary calculations, ranking, or event pagination, with the inclusive counterparty-cohort exception defined above. The only address-type choices are `EOA` and `Contract`; selecting both means all rows, including unresolved internal failures, while selecting one excludes the other and unresolved rows. The dashboard renders exact matching totals separately from the bounded rows returned to each panel and follows the event endpoint's opaque cursor on demand. The fixture demo applies equivalent non-time controls only to its small generated payload. Token recognition defaults to `All`; `Recognized` and `Other` are the only classification labels. Hover- and focus-triggered information controls define recognition, address-type evidence, and the table's Automatic/manual override choices without requiring a persistent click-open state. EIP-7702 and unresolved address evidence remain internal.

The dashboard keeps its product identity independent from the configured wallet. A dedicated analysis-context panel presents the canonical Ethereum address as the primary subject, with the configured label as secondary context rather than a live ENS-resolution claim. It marks the static dataset as a `Historical snapshot` and live API data as the `Configured wallet`.

Static mode renders a persistent historical-snapshot disclosure beside an exact exported-versus-complete event ratio and sampling state. It identifies the Gitcoin Schelling Point multisig through an official attribution link, records complete scan coverage through a pinned Ethereum finalized block, and explains that the data is historical rather than live. The snapshot exports all 90 captured Transfer-signature rows without sampling. The shared signature still does not prove token standard or intent, and account badges remain pinned bytecode observations rather than permanent identity facts.

In live mode, the analysis-context panel also owns the completed-wallet selector, whose options retain each wallet's configured label beside its compact canonical address. Choosing an existing target changes the `wallet_address` supplied to every dashboard API query and never creates a scan job. While that request is pending, a loading indicator appears but the selector and dashboard continue to identify the last successfully loaded wallet. A transient refresh failure keeps those last-good results and provenance visible, reports the failure inline, and offers an exact-query retry instead of replacing the dashboard with the startup error state. The separate scan launcher is only for adding or advancing a target through the finalized scan pipeline. Once the API accepts a scan request, the submitted address is cleared; its launcher shows an active progress indicator even while the detail panel is closed. The panel reports only stages supported by the adapter boundary—`Queued`, `Preparing scan`, `Indexing and building analytics`, and `Validating and publishing`—and uses an indeterminate activity bar instead of presenting coarse internal checkpoints as exact percentages. Before its first analytics request, a newly opened live dashboard discovers the process-local active job. When no artifact has been published yet, it presents the target, finalized block range, named stage, and elapsed time instead of the generic unavailable state, then opens the wallet dashboard automatically after validated publication. A successful job refreshes the completed-wallet selector through a request lifecycle independent from scan polling and switches the analysis to that wallet automatically. A rejected submission keeps the typed value available for correction, while a failed running job leaves the previously published wallet artifact selected and visible. Fixture mode has no completed-wallet selector and keeps scan submission disabled.

The shared `Current selection` strip renders cumulative completed coverage as `Blocks X–Y · Finalized`. It uses run-backed snapshot fields, never minimum/maximum event blocks, and visibly reports the artifact generation time. The static mainnet snapshot carries the same recorded boundary from its manifest; only the synthetic test dataset has no continuity claim. The same strip reports classified versus eligible address counts and successful observation blocks; its hover text gives both address-level and event-weighted denominators plus failed and not-checked address counts.

The primary overview pairs a zero-based stacked bar timeline with the Top Counterparties ranking to keep the time pattern and ranked addresses visible together. The timeline splits captured Transfer-signature event counts into inbound, outbound, and neutral self direction. Its labeled event-count axis shows the zero baseline, three intermediate values, and the current maximum; immediate hover and keyboard-focus details expose each bucket's exact total and directional composition. Self events remain in the total but are never folded into inbound or outbound. `All years` is the default and fits the complete observed range into yearly bars. A single year dropdown avoids a row of year buttons; choosing a year, or clicking its overview bar, applies that exact UTC year to the dashboard and replaces the chart with monthly bars for that year. Clicking a month narrows summary cards, ranked tokens, ranked counterparties, and recent events to that exact inclusive-start/exclusive-end month; clearing the month returns to the selected year, while `All years` removes the time scope. The API derives counts from complete filtered `wallet_events`, but bucket positions come from the unfiltered observed calendar domain so recognition, account, or search changes cannot make time positions jump. The calendar period containing live data generation is marked partial. The fixture demo permits year/month chart navigation but disables dashboard period cross-filtering because its bounded export cannot prove complete per-period results.

An explicit RPC enrichment step selects every distinct event counterparty exactly once after excluding the configured wallet and zero address. It resolves one concrete `safe` block (or a configured confirmed-head fallback), batches `eth_getCode`, and checkpoints results in a separate ignored DuckDB cache. Exact 23-byte code beginning `0xef0100` preserves its target as internal `eip7702_delegated` code state but remains an EOA candidate for public presentation; empty code is `eoa_candidate`; other code is `contract`; and failed reads are retryable `unknown`. Successful rows are never automatically refreshed. The stored block number, hash, timestamp, finality policy, fetch time, and reason make the historical observation explicit; no-code evidence does not prove an EOA, personhood, control, or permanence.

The packaged `app:enrich` operation requires an explicitly configured RPC and remains
separate from `app:up`. It checkpoints only missing evidence, then reprocesses each completed
wallet's cumulative finalized range into a staged copy so historical rows receive the shared
classification without changing raw evidence or scan coverage. Publication requires exact
preservation of immutable event facts, orchestration tables, wallet targets, and application
overrides. Evidence-cache progress survives a failed analytical publication and remains retryable.

Safe and ERC-4337-specific collection are intentionally removed. A deployed Safe or smart account with bytecode is ordinary contract evidence. A counterfactual address with no code can appear as an EOA candidate under this deliberately bounded binary presentation; that limitation is disclosed rather than hidden behind speculative subtype detection.

Visible blockchain identifiers are Etherscan navigation targets. Token-activity symbols, their compact emitting-contract addresses, and event symbols link to `/token/{address}`, counterparty addresses link to `/address/{address}`, and event transaction controls link to `/tx/{hash}`. All navigation opens a new tab without granting the destination access to the dashboard window.

The local API returns a bounded counterparty page for the active filter selection, while the dashboard defaults to 10 and lets the user display 10, 25, or 50 ranked addresses. The Ethereum zero address is excluded from the ranked counterparty summary because it represents token mint/burn mechanics rather than a navigable counterparty. The ranking also excludes the configured wallet itself and addresses observed as emitting token contracts. Their captured events remain in `wallet_events`, timeline counts, token summaries, totals, and event-query results so the underlying indexed evidence stays complete.

A self-transfer, whose emitted `from` and `to` both equal the configured wallet, is labeled `self` before either directional branch is evaluated. It remains one event and contributes to total and per-token self counts, but contributes to neither inbound nor outbound counts, external counterparty totals, or timeline directional stacks. The underlying zero-address, emitting-contract, and self event rows remain in event and token-flow analytics.

The dashboard identifies itself as Transfer Event Analytics and states concisely that it is based on emitted `Transfer(address,address,uint256)` events. The Top Counterparties panel sits to the right of the timeline at normal desktop widths, ranks eligible addresses by the sheer number of captured Transfer-signature events—not proven ERC-20 events or distinct transactions—and aggregates each address into one row. Under a Recognized or Other selection, an address qualifies when it has at least one event in that cohort; mixed addresses retain their full activity across both recognition states. It shows observed-at address-type evidence, emitting-contract breadth, `Inbound / Outbound Events` counts, and recency. The EOA/Contract multi-select scopes the ranking, events, timeline, token summaries, and statistics. The Token Activity panel occupies the full row below that overview and aggregates matching account-evidence cells back to one row per emitting contract before ranking by captured Transfer-signature event count. Both ranked panels fit their cards without horizontal scrolling and use compact labeled row cards on narrow screens; their bounded vertical regions retain a themed scrollbar. Token rows expose rank, symbol/name, compact canonical address, exact event count with a maximum-relative comparison bar, inbound/outbound/self event counts, exact confirmed-indirect counts, and distinct non-zero/non-self counterparties with sender/recipient detail. The bar encodes event frequency only; raw third values and cross-contract quantities are not presented. Recent events are paginated client-side in groups of 10.

Transaction initiation remains a separate event-time evidence layer from observed-at account and token classification. `direction` is still derived only from emitted Transfer `from`/`to` relative to the configured wallet and has values `in`, `out`, or `self`. An event is `is_indirect = true` only when a selected top-level transaction sender exists and differs from Transfer `from`; it is false on an observed match and null for legacy rows without sender evidence. Sender and target relation codes describe exact address equality against Transfer participants and the emitting token contract. Recent events append `*` to `in` or `out` for confirmed mismatches; self uses a neutral badge and explains that both event participants are the tracked wallet. Recognition does not change these fields or establish transaction-sender intent. The mismatch does not establish execution path, intent, standards compliance, economic ownership, legitimacy, or historical account type.

Theme changes update the dashboard palette in place and retain the preference locally.

Local API responses carry HyperIndex/DuckDB provenance, complete matching counts, minimum/maximum observed event and account-evidence block/time bounds, scan coverage, returned row counts, and configured query limits. The dashboard renders a block range for mixed enrichment batches and a single block only when both bounds match. The static `dashboard-export-v1` metadata projects the mart contract explicitly, reports the checked-in snapshot's finalized scan boundary and event extrema separately, and computes complete/returned counts and sampling state from the exact relations exported. Neither path may imply freshness beyond its recorded endpoint.

## Token Label Flow

`scripts/sync_token_registry.py` explicitly fetches Ethereum token evidence from Trust Wallet, Uniswap, CoinGecko, and Coinbase Exchange and writes a checked-in snapshot plus provenance manifest. Coinbase entries require an online currency with an online Ethereum network and an exact contract address; Coinbase trading precision is never treated as ERC-20 decimals. Matching is by exact Ethereum contract address, never name or symbol. It is never invoked by dbt or the dashboard, so normal builds do not depend on network availability or mutable upstream data.

Automatic `recognition_status` is `recognized` for exact-address membership in at least one selected registry and `other` when no match exists. Reviewed seed and live DuckDB overrides may explicitly select either result. `recognition_reason`, `recognition_source`, and `token-recognition-v1` preserve why the result was assigned. `metadata_availability` reports whether name, symbol, and decimals are `complete`, `partial`, or `unavailable`; it says nothing about recognition or safety.

Registry absence is neutral: it produces `other`, not a negative safety claim. The local API calculates complete counts for the active recognition and inclusive account selection so summary cards do not mistake paginated rows for full matching history.

RPC enrichment is a separate explicit batch operation. It ranks `other` contracts by wallet transfer count, pins one Ethereum block, and reads optional token `name`, `symbol`, and `decimals` methods. Results are stored in an offline seed with `complete`, `partial`, or `failed` fetch status. Merge precedence is manual override, curated registry, then RPC metadata. RPC rows never establish recognition.

## Recognition Policy

`Recognized`/`Other` is derived from exact-address registry membership and local manual overrides. Token names, symbols, registry absence, and wallet-token activity patterns are not scored for reputation or legitimacy. Indirect counts and transaction relation codes remain descriptive evidence only.

Runtime settings resolve from shell environment first, git-ignored `config.yaml` second, and the configured public RPC fallback last. The fallback is allowed only for read-only Ethereum metadata. Envio and live Postgres credentials remain required for their respective operations.

## Fixture Demo Export Policy

GitHub Pages is a portfolio demonstration, not the complete application runtime. Its generated JSON must come from the reviewed checked-in historical mainnet snapshot, remain small enough for static hosting, and display wallet attribution, finalized scan provenance, enrichment observation bounds, exported-versus-complete counts, sampling state, and historical-not-live status prominently. It may demonstrate filters and interactions without claiming current wallet state.

The exporter evaluates the nine non-empty recognition/address-evidence selections needed by the static demo. Complete local counts and rankings use on-demand DuckDB API queries.

Docker Compose is the supported distribution mechanism for the live local product, not for GitHub
Pages. It runs private persistent Postgres, one application runtime containing FastAPI plus the
bounded Envio/dbt worker, and an nginx-served API-mode dashboard on one loopback origin. Postgres and
analytics artifacts use separate named volumes, user keys enter only through ignored runtime
configuration, and the application uses external-Postgres `envio start` with Hasura disabled rather
than nested Docker. Process liveness is distinct from artifact readiness: the API may be live while
the initial finalized scan is still producing the first valid `live.duckdb`. Fixture build/export
commands remain outside this stack and cannot overwrite its named analytics volume.

## Scope Boundaries

- Included: wallet-relevant `Transfer(address,address,uint256)` logs on Ethereum mainnet, interpreted by ERC-20-oriented models with the explicit limitation that the source does not prove token standard.
- Included: nullable top-level transaction sender and target fields selected on those events.
- Included: exact raw third values plus separately sourced token-decimals metadata; normalized token amounts are deferred until an exact consumer contract is defined.
- Included: loopback-only scan submission for one explicit normalized address or conservatively validated ASCII ENS name per finalized interval.
- Excluded: traces, internal calls, state deltas, native ETH transfers, approvals, swaps, NFT-specific disambiguation/interpretation, USD pricing, and a publicly hosted arbitrary-wallet scanning service.

## Documentation Rule

When implementation changes, update the related documentation in the same change:

- Indexer behavior changes: update `README.md` and this file.
- Model shape or grain changes: update `docs/data-model.md`.
- Command or setup changes: update `README.md` and `docs/operations.md`.
- Local API contract changes: update `docs/data-model.md`, the server contract, and frontend client types.
- Fixture-demo JSON contract changes: update `docs/data-model.md`, `src/data.ts`, and exporter tests.
